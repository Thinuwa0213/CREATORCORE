# CreatorCore — Threat Model (Phase 1 / Gate 1)

**Status:** Analysis against the Phase 1 architecture, now `LOCKED` (several with a required amendment) as of Gate 1 approval on 2026-09-12 — see `docs/adr/README.md` for exact per-ADR status. This document identifies architectural mitigations, not implementations — **nothing here exists in code yet**. No risk below is claimed to be fully eliminated (`docs/SECURITY.md`'s no-false-guarantee rule applies here too). The "Gate 1 challenge scenarios" section below records the ten scenarios the user specifically required review against before approval, and their resolution status.

## The two-hop credential-resolution risk (surfaced during architecture review)

ADR-0006's `BotApplication ↔ GuildBotAssignment ↔ Guild` model means a credential can be reached starting from a `Guild` rather than directly from a `Tenant`. Any code resolving a `BotCredential` via a `Guild` path **must** verify that `Guild`'s owning `Tenant` matches the caller's authorized tenant — this is a second, easy-to-miss check distinct from the direct `Tenant → BotApplication` path. This is now a **required, locked** regression test in `docs/TESTING.md` and a required review item for `security-reviewer` once this code exists.

## Gate 1 challenge scenarios

The user required these ten scenarios to be specifically challenged before approving the architecture. This went through **two review rounds**:

- **Round 1** found one **CRITICAL** gap (scenarios 1/2/5/9 all depended on a worker→`BotApplication` "claim" mechanism that three ADRs cited as living in ADR-0006 — it didn't actually exist there) and one **HIGH** gap (scenario 9's multi-replica claim-handoff had no owner), plus MEDIUM issues in the push-callback direction (scenario 10) and the rotation lifecycle (scenario 8). Fixed by adding the `WorkerAssignment` claim entity to ADR-0006, the replica/claim-handoff requirement to ADR-0008, the reverse-direction (API→worker) authentication rule to ADR-0011, and the concurrency/recovery rules to ADR-0007.
- **Round 2** (verifying round 1's fixes) found the first fix was only **partially** sufficient: it specified that `apps/api` checks a WorkerAssignment claim before releasing decryption material, but never specified who is authorized to *create* that claim — leaving a worker able to self-assign a claim for a `BotApplication` it has no legitimate relationship to, relocating the original gap by one hop rather than closing it. Fixed by adding an explicit rule to ADR-0006: claim creation/renewal is an `apps/api`-side authorization decision, re-derived from the same tenant/guild/assignment ownership chain, never accepted as a bare worker assertion. A matching regression test was added (`docs/TESTING.md`) distinct from the release-side test.

**No unresolved HIGH or CRITICAL finding remains as of round 2.**

**Gate 1 recommendation implied by this table:** PASS. Item 3 (compromised API) carries the largest *accepted* residual risk — named, documented, with mandatory pre-production hardening tracked. Items 2/9 (worker blast radius/shared-fate) are accepted, documented tradeoffs with concrete revisit triggers. The CRITICAL (WorkerAssignment claim missing) and HIGH (multi-replica claim ownership) findings from the first review pass were closed by amendments to ADR-0006/0007/0008/0011 before this table was finalized — no unresolved HIGH/CRITICAL gap remains as of this version.

## No guarantee statement

None of the mitigations above make CreatorCore "secure" in an absolute sense. They reduce specific, named risks. Several rows above have explicit residual risk or open items — these are not resolved by writing this document; they are resolved by implementing, testing, and reviewing the corresponding code at Gate 1 and beyond.
